## 0. 四个问题的答案（速览）

| 问题 | 结论 |
|---|---|
| **需要翻译什么** | UI 文案集中在 `english.hpi` + `IPEnglish.hpi` 的 **40 个 TDF / 约 465 KB**，而且它们**本来就是多语言词条表**；真正的大头是 `missions.hpi` 等包里的任务简报与单位说明。全部 HPI 共 12448 个文件、2605 个文本类文件名（多数是数据定义，不是文案）。另有游戏内嵌网页约 60 万字节、位图烧字、106 个视频。 |
| **怎么翻译** | **优先走引擎自带的本地化槽**：TDF 里已有 `English/German/French/Italian/Spanish` 五种语言，写一个中文槽并让 `Language` 配置选到它。补线是任务简报 `.ota/.txt`、`.gui`、HTML、位图文字。交付形态照 ArmyMen 范式：**磁盘游戏文件不改，用运行时重定向把改过的资源喂给引擎**。 |
| **字库怎么解决** | 41BB 原生用 **`fonts/*.gaf` 位图字体**（另有 GDI `CreateFontIndirectA`）。前人的 `chn12.dot` 被证实是标准 **12×12 HZK 点阵**（24066 字 × 24 字节、GBK 索引），但它属于 v1.0 的 `gtsp.dll` 外挂链路，41BB 不加载。推荐：**扩展 GAF 字库槽位，用现成 chn12.dot 当字形数据源**，工具链复用 MajestyIIExtend 的 fontgen。 |
| **DLL hook 用什么方案** | 注入用 **Ultimate ASI Loader 的 `binkw32.dll` 代理**（41BB 主程序按名字导入它，实测），比前人「改 41 字节内联补丁」干净。前人的 hook 地址 `0x56A810` **只适配 v1.0**，41BB 必须用 IDA 重新定位。但**如果本地化槽方案跑通，可能根本不需要 hook 渲染函数** —— DLL 只负责资源重定向与字库。 |

**本轮最重要的认知转变**：上一轮把「汉化」理解成「必须在渲染函数上做文本替换」。实际上这个游戏**自带多语言文本层**，汉化的主战场从「逆向文本渲染」变成了「填官方词条表 + 解决中文字形」。这会大幅降低风险，也更契合"保留联机"的硬约束。

用你熟的词打个比方：`KINGDOMS.icd` 是业务 jar，`*.hpi` 是资源 jar，`translate/*.tdf` 是引擎自带的 `MessageSource`（按 locale 取词条），`*.gaf` 是字形贴图 Provider，注入 DLL 是一个 AOP 切面 —— 我们要做的是**换 MessageSource 的内容 + 扩充字形 Provider**，而不是在每个 `print()` 上挂切面。

### 2.2 HPI v2 容器已攻破（上一轮的最大未知，现已解决）

上一轮记为「目录异或加扰、未解出」。本轮用 TAUtil 源码 + 实测完全解出：

```
文件头 32 字节： "HAPI" + version(0x00020000) + 7 个 uint32
    dirEnd / key / dirStart / dirLen / headerSize(32) / dataEnd
dirStart 处 = 名字表：
    SQSH 块头 19 字节 = "SQSH" + version + compression + encrypted
                        + compressedSize + decompressedSize + checksum
    encrypted=1 时先做 DecryptInner： plain[i] = ((cipher[i] - (i&0xFF)) & 0xFF) ^ (i&0xFF)
    然后标准 zlib 解压  → 得到一串 NUL 结尾的文件名
例外：Jersey.hpi / terrain.hpi 的目录是**未压缩明文**，无 SQSH 头。
文件数据：从 headerSize 起顺序排 SQSH 块；部分包（english/IPEnglish/sections 等）
    一块对应一个文件，其余包用共用压缩块或明文直存，元数据在第二个目录块（索引表）。
```

> 上一轮把文件里第一处 `SQSH` 当成了「目录头」，其实那是**压缩块的 magic**，难怪试各种 XOR 流都失败。

已落地 `tools/hpi_v2.py`（纯 Python，无需 32 位 DLL），三个命令见 §7。端到端验证：`english.hpi` 的 18 个 TDF 全部导出，`gui_text.tdf` 开头正是 `/* Sections divided by corresponding GUI file name. */`。

### 2.3 ★ 最重要的发现：TDF 是引擎自带的多语言词条表

`english.hpi` 的 `translate/` 目录下 18 个 TDF 不是普通字符串表，而是**按词条分组、每词条带 5 种语言**：

```tdf
// gui_text.tdf
[Attack]
{
    German  = Angreifen;
    French  = A l'attaque;
    Italian = Attacca;
    Spanish = Ataque;
}

// death.tdf
[DEATH1]
{
    English = %s has fallen.;
    German  = %s ist gefallen.;
    French  = %s est tombé au champ d'honneur.;
    ...
}
```

对 `english.hpi` 全部 602 个数据块统计赋值键：`German / French / Italian / Spanish` 各 **1157** 条，`English` **723** 条，`piglatin` 14 条（彩蛋语言）。注意 `English` 比外语少 —— 未写 `English` 的词条，引擎直接用 `[词条名]` 当英文文本。

主程序里也确实存在 `translate`、`Language` 两个相邻字符串（`0x21A250` / `0x21A25C`），以及注册表键 `Software\Cavedog Entertainment\Kingdoms`、`kingdoms.ini`，还导入了 `GetLocaleInfoA/W`、`IsValidCodePage`、`EnumSystemLocalesA` —— **语言是配置驱动的，不是写死在代码里的**。

这意味着：**填一个中文槽 + 让配置选到它，比在渲染函数里逐词替换干净得多**，而且天然不会碰到玩家名/聊天内容（那是动态串，不经过词条表）。这与"保留联机"的约束完全同向。

### 2.4 工作量重估

- **核心 UI 文案**：约 **2300 条词条**（1157 × 2 个语言包，去重复后更少），这是全量汉化里最该先做的部分。
- **任务简报 / 单位说明**：`missions.hpi`（135 个文本类名）、`IPMissions.hpi`（77）、`data.hpi`（868）、`V3Rocket.hpi`（947）、`IPData.hpi`（423）等 —— 但这些绝大多数是 `araat.tdf`、`crebeas.tdf` 之类**单位/建筑定义**，真正要译的只是其中 `Name` / `Description` / `Tooltip` 字段，不是整个文件。
- **网页 / 位图 / 视频**：网页约 60 万字节可直接改；位图烧字需逐张；视频成本最高，建议不做。

> 结论：不要被「2605 个文本类文件」吓到。待译表应**按词条颗粒度**生成，而不是按文件数。生成方式见 §3.3。

## 3. 怎么翻译

### 3.1 三层路径

| 层 | 做法 | 优先级 |
|---|---|---|
| **A. 官方词条表**（主线） | 在 `translate/*.tdf` 的每条 `[词条]` 里写入中文。**(A2)** 新增 `Chinese` 槽 + `Language=Chinese`：IDA 已确认查表用 `_strcmpi` 且无语言白名单（`sub_543110`/`sub_543E40`），不需要 hook 词条读取；`German` 槽有版本特判，不可占用。**(A1)** 覆写 `Italian` 只作为 A2 失败时的退路 | **A2 已定**（实机待验） |
| **B. 散落文本** | 任务简报 `.ota`/`.txt`、`.gui` 界面定义、单位定义 TDF 里的 `Name/Description`、内嵌 HTML | 次之 |
| **C. 烧字资产** | 按钮/标题位图、`.gaf` 字库贴图、视频字幕 | 最后，视频可放弃 |

### 3.2 交付形态：照 ArmyMen 范式，磁盘文件不动

用户已定「保留联机」，基线文档据此要求 `KINGDOMS.icd` 磁盘哈希不变。因此推荐：

```
游戏目录（原版，哈希不变）
  + binkw32.dll        → Ultimate ASI Loader 代理（原版改名保留，如 binkw32_orig.dll）
  + scripts/*.asi      → 我们编译的 DLL
  + update/            → 覆盖层：改过的 TDF / HTML / 位图 / 字库
                          DLL 在运行时把引擎对这些资源的读取重定向到 update/
```

这样：卸载 = 删掉代理与 `update/`，游戏文件一个字节没动；联机双方读到的规则数据完全一致（只有显示文本被换），版本校验不受影响。这也正是 Majesty 的 `OverloadFromFolder` + ArmyMen 的 `update\` 两个机制的合用。

> ⚠️ 仍需验证：改动的只是显示文本时，HPI 内容校验是否会参与联机握手。设计上先按「会」处理（完全不动磁盘 HPI），实测后再放宽。

### 3.3 译文格式与校验（复用已有约定）

- **词表格式**：明文、GBK 或 UTF-8 带显式声明、每条带出处（`hpi / 文件 / 词条名 / 场景 / 是否联机可见`）。参考 Majesty 的 `#KEY + value` 与 ArmyMen 的 INI `RVA=原文|译文`。
- **安全闸门**：写入前比对"内存/资源现状 == 英文原文"，不一致就拒绝（ArmyMen 已验证能挡住地址算错改坏无关数据）。
- **容量约束**：若走内存字符串替换，中文 GBK 字节数不得超过原槽 `len(英文)+1`；词条表路线则无此限制，这也是选它的理由之一。
- **断行**：Majesty 的教训是"引擎只在空格处断行"，41BB 是否同理需实测；若同理，词典侧每汉字补 1 个 ASCII 空格并压窄空格槽步进。
- **术语表**：统一单位名、神名、阵营名（Aramon / Taros / Veruna / Zhon / Creon），逐场景校对。
- **独立校验脚本**：`verify_*.py` 单独跑，不静默容错（ArmyMen CI 三段式）。

### 3.4 联机白名单（若最后仍需 hook 渲染函数）

玩家名、聊天消息、房间名、IP/端口串都是动态内容，**绝不能进词条表查询**。按调用来源分组，联机 UI 词条单独一组；宁可漏译，不可误替换动态串。验收必须包含一次真实联机进房 + 中文房间名 + 中文聊天。

## 4. 字库怎么解决

### 4.1 41BB 的原生字体链路是 GAF，不是 dot

| 证据 | 内容 |
|---|---|
| HPI 内资源 | `fonts/` 目录含 `font12.gaf`、`font11.gaf`、`font8.gaf`、`font48.gaf`、`fontblack12.gaf`、`hattfont12.gaf`、`Times New Roman (100).gaf`，以及配套 `.pcx` / `.tdf` |
| 主程序字符串 | `Fonts\`、`Font48.gaf`、`metamap font.gaf`、`<FONT COLOR="#...">` 标签，共 30 处 `.gaf` |
| 主程序导入 | `CreateFontIndirectA`、`TextOutA`、`GetTextExtentPoint32A`（GDI32） |
| **反证** | 41BB 的 `KINGDOMS.icd` 里**搜不到** `chn12.dot` / `eng12.dot`；`gtsp.dll` 也不在导入表里 |

所以前人的「`gtsp.dll` + `chn12.dot`」是 **v1.0 时代的 GT 插件链路**，41BB 不认。那套「铁之灾祸&MOD未完全汉化」把 v1.0 组件原样搬到 41BB，很可能就是"未完全"的根因。

### 4.2 `chn12.dot` 的真相（推翻 10-03 报告的推测）

| 项 | 实测 |
|---|---|
| `eng12.dot` | 6,144 B = **256 字形 × 24 字节**；取索引 `0x41` 解出清晰的 "A" |
| `chn12.dot` | 577,584 B = **24066 字形 × 24 字节**，标准 **12×12 HZK 点阵** |
| 布局 | 每字形 12 行 × 2 字节（16 bit 大端，高 12 位有效，1bpp） |
| 索引公式 | `offset = ((lead - 0x81) * 191 + (trail - 0x40)) * 24`（GBK 双字节全范围枚举） |
| 验证 | 「一」`D2 BB` → 一条横线；「中」`D6 D0` → 完整的"中"字；ASCII 0x41 → "A" |

10-03 报告说它是「自定义容器、无格式、约 16×16 字模、需逆向」—— **错的**。它是一份**现成、完整、无加密、无校验的 GBK 点阵字库**，24066 个字形覆盖 GBK 双字节区，与 Majesty 项目里 23940 项 GB18030 字表是同一量级、同一思路。

### 4.3 三条路线与推荐

| 路线 | 做法 | 评价 |
|---|---|---|
| **A. 扩展 GAF 字库**（推荐） | 按 GBK 字表顺序把汉字字形追加进 `font*.gaf` 贴图并更新槽位表；字形数据直接取 `chn12.dot` 的 24066 个点阵，或复用 Majesty 的 `fontgen/`（Python + Pillow + 配置 YAML）从 TTF 重烘 | 走引擎原生链路，最稳；TAUtil 的 `Gaf/` + `Tdf/` + `Bitmap/Palette` 正好提供读写器 |
| **B. GDI 字体替换** | hook `CreateFontIndirectA`，把 LOGFONT 的字体名改成 SimSun/微软雅黑，让引擎自己烘焙中文字形 | 类似 ArmyMen 1 代，成本最低；但 41BB 是否用 GDI 生成 GAF 贴图需 IDA 确认，且字形风格与原版不一致 |
| **C. 沿用 gtsp.dll + dot** | 强行在 41BB 上加载 v1.0 字体代理 | 41BB 不导入 `gtsp.dll`，GT 插件接口是否保留未知；兼容性最差，**不推荐** |

推荐 **A 为主、B 备选**：先用现成 `chn12.dot` 当字形来源省掉烘字库，同时把 Majesty 的 `build_font_atlas.py` 工作流平移过来，以便日后换字体/做繁体。无论哪条路，都要遵守「字表顺序 = GB18030 字节序、槽位与下标严格一一对应」这条第一铁律。

## 5. DLL hook 用什么方案

### 5.1 注入代理：按导入表选（ArmyMen 的判据）

实测 41BB 两个主程序的导入方式：

| 模块 | 按名字导入（可作 UAL 代理） | 按序号导入（不可用） |
|---|---|---|
| `KINGDOMS.icd` ★ | `WINMM.dll`、`binkw32.dll`、`VERSION.dll`、`mss32.dll`、`DDRAW.dll`、`SHELL32.dll`、`ole32.dll`、KERNEL32/USER32/GDI32/ADVAPI32 | `WSOCK32.dll`、`DPLAYX.dll` |
| `Kingdoms.exe`（启动器） | 仅 KERNEL32 / USER32 / GDI32 / ADVAPI32 | — |

> 注意：真正干活的是 `KINGDOMS.icd`，启动器 `Kingdoms.exe` 不加载游戏 DLL。代理必须放在能被 icd 导入的路径上。

**首选 `binkw32.dll`**：① 前人的 41BB 移植版已用这个宿主，等于间接证明它在 41BB 上会被加载；② 它是 Bink 视频解码器，职责单一；③ Ultimate ASI Loader 有现成代理版本（MIT），ArmyMen/Majesty 项目里已有可复用的部署经验与许可文本。备选 `WINMM.dll`（Majesty 用的就是它）、`VERSION.dll`。

相比前人「在原版 binkw32.dll 里改 41 字节塞 `LoadLibrary`」的做法，UAL 代理的好处：不用维护二进制补丁、能通过 `scripts\*.asi` 加载多个插件、有 `update\` 覆盖层机制、卸载即复原。注意 UAL **只扫 `scripts\*.asi`**，直接丢 `.dll` 会被静默忽略；产物必须是 32 位。

### 5.2 工程与构建链

- 现成工程 `G:/Projects/TAK_41BB_CHS` 配置已对（Win32 / v141_xp / SDK 10.0.26100），只缺业务代码。补 `/utf-8`。
- 编译照 Majesty：`cl.exe /LD /EHsc /O2 /utf-8`，**Git Bash 里必须用 `cygpath -w` 把 `/c/...` 转成 `C:\...` 再放进 INCLUDE/LIB**，否则报 `C1083 无法打开 windows.h`；控制台中文提示加 `chcp 65001`。
- 或用 ArmyMen 的 `Tools/ci/build_dll_local*.py` + `msvc-wine` 在 CI 上编 v141 x86。
- 构建链三段式：编译 DLL → 组装 `update/` 载荷（词典、字库、网页）→ 独立校验脚本，任一步失败立即停止。
- 目录约定：`docs/`（编号文档）、`tools/`（Python 工具）、`inventory/`（资产清单）、`LICENSES/`（第三方许可）、`archives/`（历史脚本，不入构建）。

### 5.3 hook 点：必须重新定位

| 事实 | 说明 |
|---|---|
| 前人地址 `0x56A810` | v1.0 `Kingdoms.icd` 上是 `55 8B EC 83 EC 0C` 函数序言；在 30BB/41BB 同一位置是 `00 5E 8B E5 5D C3`（函数尾部 + NOP），全文件搜该签名均无命中 → **不可用** |
| 41BB 需要做的 | 用 IDA 打开 `dfcb2673…` 这份 icd，从 `"Language"`(`0x21A25C`)、`"translate"`、`Font48.gaf`、`<FONT COLOR=`、`.tdf` 解析错误提示等字符串做交叉引用，定位词条读取与文本渲染函数；也可用 v1.0 渲染循环的指令特征做模糊签名 |
| 已知辅助信息 | 10-03 报告保留了 v1.0 渲染循环的完整伪代码（`this + 1287*fontIndex`、每字符 20 字节字模记录、`sub_573F00` 宽度累加），可作为比对模板 |

### 5.4 好消息：渲染函数可能不用 hook

若 §3.1 的 A1 方案（覆写现有语言槽 + 切换 `Language`）验证通过，DLL 的职责就只剩两件：

1. **资源重定向**：把引擎对 `*.hpi` / `translate/*.tdf` 的读取重定向到 `update/` 里的中文副本（或在文件 I/O 层替换内容）；
2. **字库**：加载扩展后的 GAF 字库，或 hook GDI 字体创建。

这两件都不碰文本渲染循环，也就**没有逐字替换、断行、玩家名误替换**这些坑。这是本轮调查带来的最大简化。只有 A1/A2 都失败时，才退回「hook 渲染函数 + 明文整句词表」的 B 方案（此时 10-03 报告的机制仍可复用）。

### 5.5 联机约束清单（写进设计）

1. 磁盘 `KINGDOMS.icd` 保持原版哈希；所有 patch 只在进程内存。
2. 不改 HPI 里的**任何数值/规则数据**；更稳妥是完全不改磁盘 HPI，走运行时重定向。
3. hook 带来源白名单，玩家名/聊天/房间名/IP 串不参与替换。
4. 联机双方版本标识一致 —— 直接用干净 41BB 目录当基线，天然满足。
5. 验收含一次真实联机进房，只测单机不算过。
