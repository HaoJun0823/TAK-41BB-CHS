# 04 · 中文字库层（运行时纹理帧）

> 状态：**已实机验证**。主菜单按钮、悬停提示条、战役名称等中文均以真汉字渲染，
> 无乱码、无豆腐块，键盘/鼠标交互正常，连续悬停 + 静置 25 秒无异常。

## 为什么要自己做字库层

引擎的字库是「12 槽 × 256 个**单字节**字形」的 GAF 位图字体：

- 每个字形是一条 20 字节记录，`handle` 指向 GAF 里的一帧位图；
- 绘制时逐**字节**取 `handle` 贴图，没有任何 DBCS / 双字节概念；
- 字库文件里 0x81 以上确有记录，但那是 Latin-1 的半角字形，拿来画 GBK 双字节只会出乱码。

因此汉字不可能靠"换一套字库文件"解决 —— 必须在运行时**造字**。

## 已探明的引擎结构

### 字体槽（`fontMgr`，12 槽 × 5160 字节）

| 偏移 | 含义 |
|---|---|
| `+8` | 行高（绘制时直接加到 y 上） |
| `+12` | 多行时的行距（`sub_58C230` 在行数 > 1 时改用它） |
| `+16` | 首字符（字形索引 = 字节 − firstChar） |
| `+24` | 字体名指针 |
| `+28` | 已加载字形数（为 0 表示该槽还没加载） |
| `+32` | 字距（kerning）表指针 |
| `+36` | 起 256 条字形记录，每条 20 字节 |
| `+5156 / +5160 / +5164` | 该槽当前文字颜色的三个字节 |
| `+0xF1E8` | GAF 纹理对象指针（`gafObj`） |

字形记录 20 字节：`w(+0) / h(+4) / overhang(+8) / ?(+12) / handle(+16)`，
**前进量 = w + overhang**，绘制基线 = `y + 行高`。

### 关键函数（41BB，RVA）

| RVA | 函数 | 说明 |
|---|---|---|
| `0x58C230` | `DrawText(mgr, x, y, w, h, str, flags, fontIdx)` | 整段文本：换行、对齐、裁剪 |
| `0x58BF40` | `DrawGlyphRun(mgr, x, y, fontIdx, str, count)` | 单行逐字节贴图 ← **hook** |
| `0x58BD70` | `MeasureText(mgr, &w, &h, fontIdx, str)` | 量宽 ← **hook** |
| `0x58F6C0` | `AllocFrame(gaf) -> handle` | 申请一个空纹理帧 ← 调用 |
| `0x58F220` | `MakeFrame(gaf, info, palette, rec)` | 把 8 位索引位图变成纹理帧 ← 调用 |

`gafObj` 虚表：`vtbl[8] = 0x58E9A0` 即
`DrawFrame(gaf, handle, x, y, w, h, flags)`，**支持缩放**
（w/原始宽 得缩放比；flags bit1 不缩 X、bit8 不缩 Y）—— 中文就这样喂进引擎自己的贴图管线，
颜色、缩放、裁剪全部沿用引擎逻辑，不碰显存。

`MakeFrame` 的 `info` 头：`u16 w, u16 h, u16 originX, u16 originY, u8 透明索引, 7 字节填充, void* 像素 @+16`；
调色板 256 项 × 4 字节，**字节序 `[R, G, B, A]`**（`sub_58F220` 里
`(B>>3)|(G<<3)|(R<<8)` 的取值顺序可证）。

## 实现（`src/cjk_font.cpp`）

```
DrawGlyphRun 命中
  ├─ 字节 ≥ 0x81 且有后继 → 按 GBK 双字节取出
  │     → EnsureGlyph（缓存命中？造字）：GDI 宋体画 8 位索引位图
  │       → AllocFrame / MakeFrame 造纹理帧
  │     → vtbl[8] DrawFrame 画到 (cx, y + 行高 − cell)
  │     → cx += px
  └─ 拉丁段 → 攒成一整段交回原函数，自己按 w+overhang 累加前进量
```

- **字号**：`px = 行高 + 2`，单元 `cell = px + 2`（四周留 1px 透明边）。
  硬阈值把 GDI 输出转成 0/1 索引（0 = 透明，1 = 文字色），不做抗锯齿 ——
  8 位调色板里抗锯齿只会糊。
- **颜色**：读该槽 `+5156/+5160/+5164` 三字节，逐字生成对应颜色的纹理帧，
  缓存键 = 字 + 字号 + 颜色。
- **缓存**：1024 槽哈希表，线性探测 8 格。
- **兜底**：`SetUnhandledExceptionFilter` 记录异常码 / 地址 / RVA / 阶段
  （`make` 还是 `draw`），崩溃可直接回 IDA 定位。

### 一并解决换行与居中：补字距表

`sub_58C230` 在换行、居中和裁剪时**不看 `MeasureText`，而是自己按字节累加**：

```c
v16 += glyph[byte - firstChar].w + glyph[..].overhang;
if (v16 >= boxWidth) 换行;
```

双字节汉字被拆成两个字节各自查拉丁字距表，宽度全错 —— 表现为居中偏移、换行点不对、
长段落被裁掉。修法不是再挂一个 hook，而是**把 0x81–0xFE 的字距记录填成 `w = px/2,
overhang = 0`**：一个汉字两个字节正好累加成 `px`，引擎自己的换行/居中/裁剪立刻就对。

这些格子原本是 Latin-1 半角字形，但该字节区间只会出现在 GBK 双字节里、
且双字节绘制已被我们的 hook 全接管，覆盖 `w/overhang` 是安全的（`h`、`handle` 原样保留）。
实机验证：按钮文字中心从 317 移到 320，与横幅中心精确重合。

## 走过的弯路（别重走）

- **GDI 直接画 DirectDraw 主表面** → 左半屏花屏（绿紫噪点）。
  与游戏自身渲染冲突，放弃。纹理帧走引擎管线才干净。
- **`SetWindowPos(TOPMOST) + BringWindowToTop` 抢焦点** → 画面正常但**输入全部失效**
  （鼠标点不动、Enter 无反应）。游戏由测试脚本启动时本来就拥有前台权，
  不要再去抢。（`_probe/nav_test.py` 里用 `NAV_NOFOCUS=1` 关掉。）
- **按屏幕宽度换算点击坐标** → 游戏窗口是 `class="Kingdoms Class"` 的 640×480 **窗口**，
  桌面仍是 2560×1440，按桌面宽放大 4 倍就点到窗口外了。要按窗口客户区换算。
- **启动器与游戏是两个进程**：`Kingdoms.exe`（192 KB）启动后由另一个进程持有窗口，
  按 pid 找窗口会找不到 —— 按窗口类名 `Kingdoms Class` 找。
