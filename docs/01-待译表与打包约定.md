## 1. HPI v2 索引块（补上 00 文档里的最后一块空白）

00 文档 §2.2 只解出了「名字表」，其余包导不出内容，记为「元数据在目录索引块中，待解析」。
本轮解完，结构如下：

```
文件头 32B = "HAPI" + version(0x00020000) + dirEnd + key
            + dirStart + dirLen + headerSize(32) + dataEnd

@dirStart 名字表：SQSH 块（压缩+DecryptInner）或明文，NUL 结尾名字串
@dirEnd   索引块：SQSH 块（同样 comp=2 enc=1，解密顺序 dec(raw) -> zlib）
                  解压后 = 若干目录树节点 + N 条 24B 文件记录
@headerSize ... @dirStart  文件数据：SQSH 块，可能共用或明文直存
```

24 字节文件记录：

| 偏移 | 字段 | 实测 |
|---|---|---|
| +0 | `NameOffset` | 指向名字表里一个含 `.` 的 NUL 结尾名字 |
| +4 | `DataOffset` | 指向文件数据区的 SQSH 块起点 |
| +8 | `DecompressedSize` | 必须等于 SQSH 头的 `DecompressedSize` |
| +12 | `BlockSize` | 必须等于 `19 + CompressedSize` |
| +16 | `?` | 同一包内恒定 |
| +20 | `?` | 逐条变化，疑为内容校验 |

**记录起点不固定**：前面穿插目录树节点，数量随包内目录数变化（00 文档里
「固定 12 字节头 + N×24」的假设只在 `english.hpi` 上凑巧成立）。因此
`tools/hpi_v2.py` 不假定起点，而是**逐 4 字节扫描整个索引块**，用四项强约束
（名字含点、偏移落在数据区且是 SQSH 起点、解压长度吻合、块总长吻合）筛出真记录，
再用 `(NameOffset, DataOffset)` 去重。四项同时吻合几乎不可能误报。

验证：`python tools/hpi_v2.py verify "<41BB目录>"` → **9037 条记录逐条重读，0 失败**。
路径通过「名字表里该名字之前最近一个不含点的名字」推断，实测还原出
`translate/gui_text.tdf`、`missions/takmission23_ph.ota`、`guis/BattleMenuSingle.gui` 等正确路径。

例外：`terrain.hpi`（132 MB）无索引块，是明文名字表 + 地形贴图，不含文本资源，不影响汉化。

## 4. workflow 打包约定

沿用 ArmyMen 的**三段式**：编译 → 组装 → 独立校验，任一步失败立即停止。
本仓库当前提供「组装」段的接口与实现骨架：

```yaml
# 示意，完整 workflow 等 DLL 方案定稿后补
- name: 校验明文表
  run: python tools/verify_strings.py --text text
- name: 组装资产
  run: python tools/build_assets.py --text text --out build_out --slot Italian --strict
- name: 编译 DLL（待补）
  run: python Tools/ci/compile_dll_wine.py ...
- name: 独立校验产物（待补）
  run: python tools/verify_release.py build_out
```

### CI 模式（默认，runner 上无需原版游戏）

`build_assets.py` 只凭 `text/*.jsonl` 产出：

| 产物 | 内容 |
|---|---|
| `build_out/patches.json` | 全部已译条，按 `src` 聚合的写回指令 |
| `build_out/translate/*.tdf` | 01 组自足生成的多语言词条表，每份只含中文槽 |
| `build_out/icd_patch.json` | 06 组：文件偏移 → GBK 译文（供 DLL 内存补丁） |
| `build_out/summary.json` | 已译/未译/来源数统计 |

01 组能自足生成，是因为 `targets` 里已有 `src` + `key`（词条名），
不需要把原版 HPI 搬进仓库 —— 这对版权和 runner 体积都是必要的。

### 本地模式（`--game <41BB目录>`）

额外产出 `build_out/update/**`：把已译条改写进原始资源文本（01/02/03/04 组），
用于装上游戏做端到端验证。编码按「原单字节字符优先走 cp1252、中文走 GBK」逐字符处理，
避免整串 `encode('gbk')` 把弯引号 / 德语变音撑成双字节而破坏原文件。

### `--slot` 与编码

默认 `Chinese`：对应 **A2 方案**（新增语言槽 + `Language=Chinese`）。IDA 已确认查表用
`_strcmpi`、没有语言枚举白名单（`sub_543110` / `sub_543E40`），因此未知键名可用；
同时 `sub_49A030` 对 `German` 有版本特判，**不能占用 German 槽**。
选择 A2 而不是覆写 `Italian`，是为了不破坏任何现有语言的行为。

仍待实机确认的是「`Language=Chinese` 是否被写进注册表并生效」这一步，属于验证项，不是方案假设。

## 5. 尚未解决（下一步，与 IDA 直接衔接）

1. **语言槽是否生效** —— `Language` 的取值范围、读取来源（注册表 / `kingdoms.ini`）、
   引擎是否接受新键名、是否按 DBCS 取字形。这是整个方案的分岔点。
2. **HPI v2 重打包** —— `update/` 里的散文件要变成引擎能读的资产，要么写 HPI v2 writer，
   要么由 DLL 在文件 I/O 层做运行时重定向。后者更符合「磁盘 HPI 哈希不变」的联机约束。
3. **HTML 保留标签结构的段落替换** —— 05 组目前只有指令，需要按 chunk 索引回写而不破坏标签。
4. **06 / 07 组的去噪** —— 静态规则分不清「玩家可见文案」和「libjpeg / DirectDraw 报错」，
   必须用 IDA 对字符串做交叉引用，看哪些被 UI 函数引用。确认后再把 07 的条目提升进 06。
5. **字库** —— `fonts/*.gaf` 槽位表结构与扩字方案（`chn12.dot` 是现成 12×12 GBK 点阵）。
6. **联机验收** —— 真实进房 + 中文房间名 + 中文聊天，只测单机不算过。

---

## 6. 联机约束（不变）

1. 磁盘 `KINGDOMS.icd` 与所有 HPI 保持原版哈希；改动只在运行时内存或 `update/` 覆盖层。
2. 不改 HPI 里的任何**数值 / 规则数据**，只改显示文本。
3. hook 带来源白名单：玩家名、聊天、房间名、IP 串绝不参与查表替换。
4. 用干净 41BB 目录当唯一基线，联机双方版本标识天然一致。
